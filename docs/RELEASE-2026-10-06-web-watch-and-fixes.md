## 一、新功能：Edge 网页内容实时互动（`web_watch`）

### 1.1 它做什么

桌宠会读你**当前正在浏览的网页正文**，实时说一句与内容相关的话；在合适的页面类型上偶尔给一条建议。

实机跑出来的原话（站点与当时页面内容相关，可对照日志）：

| 场景 | 桌宠说的话 |
| --- | --- |
| 一篇讲「桌面宠物为什么不长久」的文章（`page_dwell`） | 「原来频繁打断用户三天就能劝退，这数据太真实了」 |
| 技术页停留（`page_dwell`） | 「放弃谈判直接动手，这次行动够干脆利落！」 |
| 划词选中一段文字（`selection`） | 「8% CPU 换 60fps 这性能优化可以啊」 |
| 长文页久留（`page_idle_suggestion`） | 「建议收藏这篇文章并添加标签……」 |

### 1.2 怎么实现（数据流）

```
Edge 扩展（MV3）
  content.js  采集当前页：标题/正文摘录/小标题/划词/视频进度
      ↓ chrome.runtime.sendMessage
  background.js  队列 + 端口自愈 + 失败重试
      ↓ fetch POST http://127.0.0.1:<port>/event   （带 X-Pet-Token）
桌宠 pet/web_watch
  server.py   ThreadingHTTPServer（只绑 127.0.0.1，令牌校验，正文上限 64 KiB）
      ↓ 队列（HTTP 线程 → GUI 线程用 Qt 信号唤醒，事件即处理）
  policy.py   触发状态机：停留 / 正文增量 / 划词 / 视频时刻 / 发呆建议
      ↓ 去重（页级）+ 门禁（可见、全屏、发呆、Agent 忙）
  llm.py      复用你已配置的聊天 provider 生成 ≤40 字短评
      ↓
  共享代理（多窗/多宠统一）冒泡 + 可选 TTS
```

### 1.3 隐私与安全边界（设计如此）

- **只连本机**：接收端只绑 `127.0.0.1`，不监听外网；
- **令牌鉴权**：32 位十六进制令牌，`hmac.compare_digest` 比较，401 计数可在状态里看到；
- **URL 进门前脱敏**：查询串与片段（`?utm_source=…`、`#anchor`）在入口就丢弃，永不入库/入日志；
- **日志不落内容**：只记域名与长度（`正文=N字 划词=N字`），不记标题与正文；
- **默认全关**：`web_watch.enabled` 默认 `false`，要用得自己去设置页打开；
- **可屏蔽**：设置页提供域名黑名单/白名单（例如把 `127.0.0.1` 加黑名单，避免它评论你正在看的本地页面）。

### 1.4 怎么用（三步）

1. 打开 `edge://extensions` → 打开「开发人员模式」→「加载解压缩的扩展」→ 选
   `integrations/edge-web-watch/` 目录（或安装目录下 `_internal/integrations/edge-web-watch`）；
2. 在该扩展的「扩展选项」里填**端口**（与桌宠设置页一致）与**令牌**（桌宠设置页可复制），点「保存」→
   「测试连接」；连不上就点「自检」，它会打印端口、主机权限、Service Worker 生产路径与候选端口扫描结果；
3. 桌宠设置页 →「自动化与联动 → 网页互动」→ 打开开关 → 正常浏览网页。

> 建议先把 `dry_run`（验证模式）打开跑一天：它只写日志不调模型、不花额度，日志里能看到
> `收到事件 → 判定命中 → 派发` 三段，确认符合预期再关掉它开始真正说话。

### 1.5 可调项（设置页 →「网页互动」）

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 换页停留门限 | 8 秒 | 打开页面后至少停留多久才评论；想「一打开就说」调 0~1 秒 |
| 同页冷却 | 2 分 | **只管同一页刷屏**；换到新页面不受它限制 |
| 最小请求间隔 | 15 秒 | 跨页面的硬保护，防免费档被限流 |
| 每日上限 | 60 条 | 到量当天不再说话 |
| 正文摘录长度 | 600 字 | 越小越快、越省 token，评论也越「泛」 |
| 先说一句「让我看看……」 | 开 | 命中后立刻给反馈，再等模型答复 |
| 语音朗读 | 关 | 复用语音报时通道把评论读出来 |

## 二、反应速度（实测，不是形容词）

### 2.1 改动前（同一台机器、同一模型，8 条真实回复的日志时间戳）

| 阶段 | 实测 |
| --- | --- |
| 网页事件到达 → 策略判定 | 0 ~ **5 秒**（页面「说完话」后心跳退避到 5s，新页面白等） |
| 判定命中 → 发出模型请求 | 通常 0s，**最差 30 秒**（全局冷却把新页面也一起拦了；被拦时每秒重算一次直到窗口过期） |
| 发出请求 → 收到回复（模型往返） | 中位 **3.98s**，最快 0.86s，最慢 **18.85s**，另有 >36s 无响应 |
| 典型端到端 | ~4 秒；最差 ~25 秒；卡住时最长静默 **3 分钟**（60s 超时 × 3 次尝试） |

### 2.2 改动后

| 阶段 | 实测 |
| --- | --- |
| 事件到达 → 判定 | **0.000 ~ 0.002 秒** |
| 判定 → 派发 | **0.008 ~ 0.111 秒** |
| 派发 → 回复 | 0.885 秒（本轮样本） |
| **端到端（打开页面 → 冒泡）** | **0.998 秒** |

日志原文（`14:23:21.594` 收到事件 → `14:23:22.592` 回复）。

### 2.3 用了哪些手段

1. **事件到达即唤醒**：HTTP 线程发 Qt 信号，GUI 立刻处理并把心跳拉回 1s（120ms 去抖），不再赌下一次心跳；
2. **换页免同页冷却**：跨页面只受最小请求间隔约束（冷却留给「同一页别刷屏」）；
3. **频控下限按功能分开**：网页互动 10s / 0.1 分，主动识屏仍是 30s / 0.5 分（共享 clamp 曾把配置的 12s 顶回 30s）；
4. **被拦不丢、不过期**：记住这条内容，冷却过后仍在本页就补说、已经翻页则丢弃（原来是每秒重算到窗口过期，说的还是过期内容）；
5. **先兆气泡**：派发瞬间冒「让我看看……」（不朗读、不占时长）；
6. **更短的请求**：正文摘录 1200 → 600 字，`max_tokens` 512 → 192；
7. **卡住快速失败**：单次超时 60 → 30 秒，尝试 3 → 2 次。

## 三、四处健壮性修复（都是实机踩出来的）

| 修复 | 用户看到的现象 | 根因 |
| --- | --- | --- |
| 设置页保存不再回滚未改动字段 | 「关掉语音朗读保存后，桌宠突然又连不上了」 | 设置页跑在**独立进程**，保存时把「打开那一刻」的整份旧配置写回磁盘；用户没碰过的端口/dry-run 被静默回滚。修法：逐字段比对打开时的界面快照，没碰过的以**磁盘最新值**为准 |
| 扩展端口自愈 | 「刚才还好好的，怎么又连不上」 | 端口不一致时 `fetch` 只报 `TypeError`，与权限/策略问题无法区分。修法：扩展在候选端口里找桌宠签名（`/health` 的 `ok:true`），缓存 60s，失败强制重扫并换端口重试，弹窗提示「桌宠在 X，建议改成 X」 |
| 热加载路径同步 | 「设置里开了，接收端却不启动」 | `AppShell._apply_external_config_change()` 没接线到 `web_watch` |
| 事件先记录再判守卫 | 「开了却一句话都不说」 | 门禁（Agent 忙 / 不可见）先于页面身份记录执行，事件被整条丢弃且不留痕 |

另外补了**全链路可观测性**：日志四段（`收到事件` / `暂不说话 + 原因` / `判定命中` / `派发结论`）
+ 落盘状态快照 `web_watch_status.json`，设置页可直接看「①收到几条 ②最近判定 ③是否派发」。

## 四、修复：打包后双击弹出黑色控制台窗口

**现象**：双击安装目录的 `dsh-pet-standalone-webm-chat.exe` 后弹出一个黑色窗口，标题是 ffmpeg 的完整路径
（`…\_internal\imageio_ffmpeg\binaries\ffmpeg-win-x86_64-v7.1.exe`）。

**根因（实机进程链证据）**：

```
conhost 19800 ← 父 = ffmpeg 12552 ← 父 = 桌宠 9656
ffmpeg 12552 命令行 = …ffmpeg… -nostdin -v error -y -c:v libvpx-vp9 -i …\变鸽子.webm
                     -pix_fmt bgra -c:v libwebp -lossless 1 …\frameseq\random\…tmp\f_%04d.webp
ffmpeg 12552 MainWindowHandle = 395908（非 0 = 有可见窗口）
```

命令行特征（`-lossless 1` + `f_%04d.webp` + `.tmp`）表明窗口来自**帧序列阶段一编码**：它派生 ffmpeg 时
`creationflags` 只有 `BELOW_NORMAL_PRIORITY_CLASS`，而打包后的父进程是 GUI 子系统（PE subsystem = **2**，
**没有控制台**），Windows 于是给子进程新分配了一个**可见**控制台。

**修法**：`pet/frameseq_provision.py::_creation_flags()` 补上 `CREATE_NO_WINDOW`（+12/−1 行）。
两个标志可以并存，优先级让渡行为不变。

**验证**：

1. **A/B（用产品自身的 `_creation_flags` / `_ffmpeg_argv`，以 `pythonw.exe` 当无控制台父进程）**：
   旧标志 `0x00004000` → ffmpeg `MainWindowHandle=3672680`、出现可见窗口；
   新标志 `0x08004000` → 无窗口；
2. **部署后真产物**：删掉安装目录里 3872 个已转换帧强制重编码，像双击一样启动并盯窗 90 秒 →
   ffmpeg 有窗口句柄采样 **0 次**、无 ffmpeg 可见窗口，同时**重建 422 帧**（证明不是空转）；
3. 换一条启动路径（开机自启的 `cmd /c start`）复测 40 秒：ffmpeg 在 200 次采样中 130 次在跑，
   可见窗口 **0** 个；
4. 顺带排除项：`exe` 自身是 GUI 子系统（读取 PE 头：当前安装/原始备份/本次构建三者 subsystem 均为 2）、
   `harness_autostart=false`、`click_sound` 那处 `Popen` 是 macOS/Linux 回退、开机自启命令实测**不闪窗**。

## 六、已知问题与未做的部分（如实登记）

1. **表情包配图未接入**：网页评论目前只出文字气泡（+可选 TTS）。原因是三个宿主
   （`PetWindow` / `OverlayShell` / `MultiWindowProxy`）都没有公开的 `show_image` 扇出面；
2. **流式输出未实现**：模型首字到达即冒泡可以把感知延迟再压到 1~2 秒，需要新增 SSE 解析与气泡增量更新；
3. **模型往返方差仍存在**：同一配置实测 0.86s ~ 19s，偶发 >36s；代码侧只能「先兆气泡 + 快速失败」，
   想更快建议在「AI 与对话」里换更快的 provider/模型档位；
4. **帧序列供给是启动时的重活**：首次启动/素材变化后会在后台重编码（预算 120 秒，剩余留到下次启动），
   期间 CPU 占用明显、界面可能有一次秒级卡顿（实机日志里出现过 `max=2372ms` 的单次 tick 间隔）；
5. **「关掉那个黑窗导致桌宠卡死」的报告未能复现**：实测在转码过程中强杀 ffmpeg 子进程，
   桌宠 `Responding=true`、日志继续增长、供给继续起下一个 clip（未卡死）。该窗口本身已由第四节修复消除，
   其触发条件随之消失；若你仍能复现卡死，请带上 `%APPDATA%\dsh-pet-standalone-webm-chat\pet-<pid>.log`
   的最后 50 行提 issue。
